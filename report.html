1. Executive Summary & System Overview

The Student Placement & Job Portal is a production-grade enterprise web application designed to automate and streamline campus recruitment activities in university institutions. It establishes a unified, secure digital bridge between graduating students, corporate recruiter partners, and university placement administrators.

1.1 Core Problems Solved

  • Automated Academic Eligibility Filtering: Prevents unqualified applications by automatically verifying minimum aggregate CGPA thresholds and eligible academic branches before submission.
  • Duplicate Application Elimination: Database-enforced composite unique constraint (student_id, job_id) prevents accidental double-submissions.
  • Role-Based Access Control (RBAC): Separates student self-service capabilities (browsing jobs, tracking status, uploading resumes) from administrative governance (creating jobs, approving companies, changing application stages).
  • Full Auditability: Every status transition (APPLIED → SHORTLISTED → SELECTED / REJECTED) records an unalterable history log detailing the administrator ID, remarks, and timestamp.

1.2 Layered Enterprise MVC Architecture

The application strictly follows the Model-View-Controller (MVC) enterprise design pattern using clean separation of concerns without relying on heavy abstractions or third-party ORMs:

2. Implementation of Java Servlets (Jakarta Servlet 6.0)

Java Servlets serve as the Controller in the MVC pattern. They intercept incoming HTTP requests, process business operations via services, update models, and route responses to appropriate JSP views.

2.1 Servlet Lifecycle & Execution Model

Servlets adhere to the standard Jakarta Servlet lifecycle managed by Apache Tomcat 10.1:

  1. Loading & Instantiation: Tomcat loads servlet classes upon the first request or at container startup via load-on-startup.
  2. Initialization (init()): Initializes resources and service instances once per servlet lifetime.
  3. Service Execution (service() / doGet() / doPost()): Dispatches HTTP methods across concurrent thread pools.
  4. Destruction (destroy()): Invoked when the web application undeploys or container halts, gracefully releasing resources.

2.2 Servlet Filters for Enterprise Cross-Cutting Concerns

Four specialized jakarta.servlet.Filter implementations safeguard the application:

Filter Name URL Mapping Responsibility
EncodingFilter /* Forces UTF-8 character encoding on all requests and responses; injects standard HTTP security headers (X-Frame-Options: SAMEORIGIN, X-Content-Type-Options: nosniff).
AuthenticationFilter /admin/*, /student/* Verifies active HttpSession; captures unauthenticated requests and stores return URLs before redirecting to /login.
AuthorizationFilter /admin/*, /student/* Enforces Role-Based Access Control (RBAC). Prevents students from accessing admin URLs and returns HTTP 403 Forbidden via /WEB-INF/views/error/403.jsp.
CsrfFilter /* Generates and verifies cryptographic session tokens for all state-changing HTTP requests (POST, PUT, DELETE).

2.3 Session Management & Fixation Protection

To prevent Session Fixation Attacks, LoginServlet invalidates the pre-authentication session identifier upon successful credential verification:

Uploaded files are validated against allowed MIME types (application/pdf), renamed to randomly generated UUIDs to eliminate path traversal vulnerabilities, and streamed securely through ResumeServlet with appropriate cache headers.

3. Implementation of JSP (JavaServer Pages), JSTL & Expression Language

In modern Advanced Java architecture, JSP acts purely as the View. Java scriptlets (<% ... %>) are completely deprecated and replaced with standard Expression Language (EL) and Jakarta Standard Tag Library (JSTL).

3.1 Standard Tag Library (JSTL 3.0) Integration

All dynamic iterations, conditional displays, and formatting utilize Jakarta Standard Tag Library (jakarta.tags.core and jakarta.tags.fmt): 

<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>

<!-- Conditional Status Rendering -->
<c:choose>
    <c:when test="${u.role == 'ADMIN'}">
        <span class="badge bg-danger-subtle text-danger">ADMIN</span>
    </c:when>
    <c:otherwise>
        <span class="badge bg-primary-subtle text-primary">STUDENT</span>
    </c:otherwise>
</c:choose>

3.2 Modular Templating Structure

Views are decomposed into maintainable, reusable components included via <jsp:include>:

  • common/header.jsp: HTML5 document head, meta tags, and local-first Bootstrap 5.3 stylesheet declarations.
  • common/navbar.jsp: Dynamic, role-sensitive navigation bar that switches seamlessly between Public, Student, and Admin menus.
  • common/alerts.jsp: Flash alert messaging system rendering session notifications (flashSuccess, flashError) with auto-dismissal.
  • common/footer.jsp: Standard institutional footer, copyright information, and JavaScript bundle dependencies.

3.3 Strict 6-Jobs-Per-Page Pagination Implementation

To avoid overwhelming students with 26 long job cards, the portal implements a strict 6-jobs-per-page view with intuitive down-arrow navigation:

  • Initial Render: Only cards with indices 0..5 are visible; cards with indices 6..25 are hidden using CSS d-none.
  • Page Transitions: Clicking "Next 6 Jobs ↓" or numbered page buttons (1, 2, 3, 4, 5) hides the previous 6 cards and displays only the newly selected 6 cards.
  • Viewport Positioning: Automatically executes smooth scrolling to the top of the jobs grid so new job openings appear directly in view without endless downward scrolling.

4.2 Equivalent Controller Implementation in Spring MVC

The following example illustrates how our pure AdminJobServlet would be written in modern Spring MVC: 

// Spring MVC Equivalent Controller
@Controller
@RequestMapping("/admin/jobs")
public class JobController {

    private final JobService jobService;
    private final CompanyService companyService;

    @Autowired
    public JobController(JobService jobService, CompanyService companyService) {
        this.jobService = jobService;
        this.companyService = companyService;
    }

    @GetMapping
    public String listJobs(@RequestParam(required = false) String search,
                           @RequestParam(required = false) String status,
                           Model model) {
        model.addAttribute("jobs", jobService.searchJobs(search, status));
        model.addAttribute("companies", companyService.getAllCompanies());
        return "admin/jobs";
    }

    @PostMapping
    public String createJob(@Valid @ModelAttribute JobDTO jobDTO, 
                            BindingResult bindingResult, 
                            RedirectAttributes redirectAttributes) {
        if (bindingResult.hasErrors()) {
            return "admin/jobs";
        }
        jobService.createJob(jobDTO);
        redirectAttributes.addFlashAttribute("flashSuccess", "Job posted successfully!");
        return "redirect:/admin/jobs";
    }
}

6. Database Design & JDBC Data Access Layer

6.1 Relational Schema Architecture

The database schema placement_portal contains 6 normalized relational tables:

Table Name Primary Key Foreign Keys & Key Constraints Purpose
users user_id email UNIQUE Authentication credentials, BCrypt password hashes, account status, and role (ADMIN / STUDENT).
students student_id user_id → users(user_id), enrollment_number UNIQUE Academic profiles, branch, semester, CGPA, phone, and resume storage path.
companies company_id company_name UNIQUE Recruiter partner organizations, industry sectors, location, and HR contacts.
jobs job_id company_id → companies(company_id) Campus job drives, titles, descriptions, minimum CGPA, eligible branch, and deadlines.
applications application_id job_id → jobs, student_id → students, UNIQUE(student_id, job_id) Student applications, status tracking (APPLIED, SHORTLISTED, SELECTED, REJECTED).
application_status_history history_id application_id → applications Unchangeable audit trail recording previous status, new status, timestamp, and changing admin ID.

6.2 High-Performance Connection Pooling (HikariCP)

Rather than creating expensive new database connections per HTTP request, the portal utilizes HikariCP (the fastest production connection pool in the Java ecosystem). HikariCP maintains pre-warmed connections, handles connection recycling, and automatically falls back to embedded H2 if MySQL is unavailable.

6.3 Atomic ACID Transaction Management

Multi-table operations like student registration must succeed entirely or roll back cleanly: 

Connection conn = DatabaseConfig.getConnection();
try {
    conn.setAutoCommit(false); // Begin ACID Transaction

    int userId = userDAO.create(user, conn);       // Insert User Account
    student.setUserId(userId);
    int studentId = studentDAO.create(student, conn); // Insert Academic Profile

    conn.commit(); // Commit Transaction atomically
} catch (SQLException e) {
    conn.rollback(); // Rollback on any failure
    throw new RuntimeException("Registration transaction aborted.", e);
} finally {
    conn.setAutoCommit(true);
    conn.close();
}
